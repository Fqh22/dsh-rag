# dsh-rag 审视报告（2026-11-06）

> 范围：`src/`（MCP server、存储、检索、归档、体检）、`plugin/`（面板与自动注入）、`scripts/`（自测与运维）、desktop / web profile 配置。
> 方法：读代码 + 只读查生产库 + 最小复现 + 跑自测 + 两个并行子审查。**没有修改任何生产代码或数据**（除新增本文档）。

## 0 · 结论

> 本文写于修复前；下面的问题已**全部修掉**（两批），改动与验证见 **§7**。

骨架是好的：分层清楚、数据干净、自测能跑通。但有 **3 个 P0**，其中两个直接让产品的核心卖点失效：

1. **pack 的预算裁剪把「当前状态」砍成空、把最新事实丢掉**，只留最旧十几条 —— 最活跃的两个项目已经中招；
2. **`checkpoint_put` 单独改 baseline 是静默 no-op** —— 缓存前缀的地基改不动，工具还报「已更新」；
3. **自测会写生产导出文件** —— `dsh-rag/交接卡.md` 已经被测试字符串覆盖。

另外三条红线被绕过：`recall` 不做项目名归一、`prune` 硬删无备份、两个归档入口（watcher 进程 + MCP 启动线程）并发写库无协调。

## 2 · P0

### P0-1 · pack 裁剪先砍「当前状态」，再砍最新事实

**位置**：`src/card.py:145-170`

```python
# 顺序：next → card 尾部 → facts 尾部。基线永远不砍
if total() > limit_chars and sections["card"]:  sections["card"] = sections["card"][:keep] or ""
if total() > limit_chars and sections["facts"]: sections["facts"] = sections["facts"][:keep]
                                                                        # ↑ 保留开头 = 最旧
```

`facts` 按 id 升序（旧 → 新）拼接，`[:keep]` 保留的是**最旧**的一批；提示却写「…（更早的事实见 recall）」，与实际相反。截断也不在条目边界，会把最后一条从句子中间切断。

**实测（生产库，只读）**：

| 项目 | pack token | baseline | facts | **card** | truncated |
|---|---|---|---|---|---|
| dsh-rag | 3011 | 437 | 4316 | **0** | card,facts |
| companion-bot | 3011 | 443 | 4304 | **0** | card,facts |
| 工作区 | 2428 | 0 | 2890 | 935 | — |

dsh-rag 的 27 条 active 事实共 10784 字符（≈6740 token），3000 预算只装下 **15 条、id 2..108**（项目最早期的内容）；11-01 之后写的全部不可见。pack 末尾是半句「2) 异常没有 rollback，sql」+「…（更早的事实见 recall）」。

**最小复现**（40 条事实、budget=800）：`sections.card=0`、保留 fact id `1..6`、第 6 条被腰斩、`has card text? False`。

**为什么测试没抓到**：`scripts/selftest_v5.py:128-130` 只断言「裁剪有记录 / chars 变小」，没断言 card 必须存在、保留的必须是最新事实。

**影响**：越活跃的项目越坏。新会话读到的包没有当前状态、没有最近决策 —— 而 pack 存在的理由正是替代手工交接。

**修复**：裁剪顺序改 `next → facts → card`；facts 从尾部保留（最新）、按 `\n\n` 在条目边界切、提示放开头；单条事实进 pack 限长（400 字符左右）；给 selftest_v5 补「card 非空」「保留的是最大的 id」两条断言。

### P0-2 · 单独改 baseline 静默失败（`checkpoint_put` 复用 `remember` 的 hash 不含 meta）

**位置**：`src/store.py:222-224,252-269,367`；`src/card.py:62-85`

`remember()` 的去重键是 `project + title + content`，**不含 meta**；而 `render_card()` 不渲染 baseline（baseline 只在 `build_pack` 里出现）。所以：

```python
checkpoint_put(p, {"baseline": "NEW"})
# → card_text 与旧卡逐字节相同 → content_hash 命中 → created=False
# → meta_json 不更新，工具仍返回「交接卡已重渲染」
```

**实测**（临时库）：

```
after1 baseline = 'OLD' id 1
after2 baseline = 'OLD' id 1  created False   # 期望 NEW
meta changed: False
```

**影响**：baseline 是「稳定前缀、跨会话复用缓存」的地基。技术栈/目录/红线变了想更新，调用成功但没生效，pack 一直用旧基线，没人知道。

**修复**：checkpoint 不走 `remember` 的去重路径 —— 按 `project + kind='checkpoint' + status='active'` 原地 `UPDATE`（同时写 FTS/meta），或把 `meta_json` 纳入 hash。

### P0-3 · 自测写生产导出文件，`dsh-rag/交接卡.md` 已被覆盖

**位置**：`scripts/selftest_store.py:13-17`、`scripts/selftest_mcp.py:32-33`、`src/store.py:324-329`、`src/projects.py:131-158`

自测正确地用 `DSH_RAG_DB` 指向临时库，但 `put_handoff()` 末尾会写磁盘：

```python
projects_mod.write_handoff_md(project, md_content, ...)   # 路径来自 PROJECTS_ROOT，与 DSH_RAG_DB 无关
```

**证据**：`Projects/dsh-rag/交接卡.md` 当前正文正是 `selftest_store.py:17` 的字面量「当前进展：已完成存储层。下一步：MCP server。」（mtime `2026-11-05 21:03:06`）。`data/handoffs/p.md` / `p1.md` 也是测试产物。`.gitignore` 忽略了 `交接卡.md`，所以 git 也看不出来。

**修复**：路径层加 `DSH_RAG_HANDOFFS_ROOT`（或在 `Store` 加 `export_md=False`）；自测统一设 `DSH_RAG_PROJECTS_ROOT` 到临时目录；用 `checkpoint_put` 重新渲染回真卡。

## 3 · P1

### P1-4 · `recall` 不做项目名归一，大小写不同静默 0 条

`store.recent()` 在 `:1102` 归一了，`store.recall()` 在 `:764` 直接用原字符串。实测 `--project DSH-RAG` / `Dsh-Rag` → **0 条且 `ok=true`**（写入侧永远归一成 `dsh-rag`）。模型会据此以为「没有历史」。修法：`recall()` 开头 `self.normalize_project(project)`。

### P1-5 · `remember()` 会复活 archived/superseded 记录

`src/store.py:259-269`：命中同 hash 时只要 `status` 不同就 UPDATE 回传入值（默认 `active`）。后果链：`cleanup.apply` 把过期会话置 `archived` 并 `DELETE vectors` → 下次 `backfill.py`（**默认 `force=True`**）重归档同内容 → `created=False` 但状态复活，且**不补向量** → 清理被静默撤销 + 这条记忆永远缺向量。修法：默认不复活，只有显式 `revive=True` 才改状态。

### P1-6 · `backfill` 强制重归档会产生第二条 active 会话记忆

`scripts/backfill.py:27-38` 默认 `force=not args.no_force`。会话变长 → 摘要变 → 新 hash → 新行；旧行没有任何按 `session_id` 失效的逻辑（全库搜不到），`sessions.memory_id` 改指新行，旧行成 active 孤儿。修法：重归档前 `UPDATE memories SET status='superseded' WHERE kind='session' AND session_id=?`；backfill 加 `--dry-run` + 自动备份。

### P1-7 · 迁移非原子、无自动备份、不拒绝降级

`schema.py:203-221` 的 `executescript` 会先隐式 COMMIT：`ALTER TABLE ... RENAME` 立即落盘，后续建表/搬数据在事务外；中途失败就停在「旧表已改名、新表半空」。`ensure()` 也没有 `version > SCHEMA_VERSION` 分支 —— 旧代码打开新库会把 `user_version` 写回去。当前库已是 v6 不会触发，但下次升级前必须补：迁移前 `sqlite3 backup`、`BEGIN IMMEDIATE` 包住、版本高于代码时拒绝打开。

### P1-8 · `pages_*` 工具裸用 `store._conn`，与启动归档线程共享连接

`server.py:631,647` 直接 `conn = store._conn` 查询，没有锁；`_startup_archive()` 在同进程另一个线程用**同一个连接**写库。`check_same_thread=False` 只关掉了检查。同类：`store.stats()` 末尾的 `schema_info(self._conn)`、`doctor.run()` 的部分查询。修法：这些路径包 `with store._lock`。

### P1-9 · `checkpoint_put` 每次新建两条记忆（写放大）

每次调用新增 1 条 checkpoint + 1 条 handoff，旧的置 superseded；每张卡还触发一次付费 embedding。生产库 331 条里 `checkpoint(superseded) 61` + `handoff(superseded) 56` = **117 条（35%）**；`cleanup.plan` 一次列出 100 条 / 99.9 KB；companion-bot 一天产生 30+ 张卡。修法：主行原地更新，历史压进 `meta.revisions`（留最近 N 版）或独立 `checkpoint_history` 表。

### P1-10 · `prune` 是不可逆硬删，没有备份

`plugin/index.js:330-337` 只校验 `confirm === true` 就调 `prune --confirm`；`store.delete_project()` 直接 `DELETE memories/vectors/fts/sessions`。唯一防线是前端一个 `window.confirm`，而「清理」按钮基于 10 秒轮询的 `hasDir` 快照 —— 目录临时改名/断网盘时仍会显示，一点就清空整项目记忆。违反工作区「破坏性操作先备份」红线。修法：删前 `shutil.copy(memory.db)` 或走 `archived`（已有 `restore`）；前端要求输入项目名，并先返回 dry-run 条数。

### P1-11 · web profile 的 MCP 配置还是旧写法

`~/.dsh/profiles/web/cordis.patch.yml:7` 是 `- id: dsh-rag`（按 id 覆盖）而不是 `- insert:` 包裹。id 不存在时**静默忽略** —— desktop 修过这个坑，web 没修。用 web profile 起 DSH 时 MCP server 不启动、工具不出现、零报错。

### P1-12 · `restore` 只改状态，不重建向量

`cleanup.apply` 归档时 `DELETE FROM vectors`；`store.restore_memory()` 只 `UPDATE status='active'`。恢复后这条记忆关键词能搜到、语义永远搜不到（正是项目反复强调的坑）。修法：restore 时若缺当前模型向量就重 embed。

## 5 · P3（小项）

- `doctor.py:82` 指向不存在的 `scripts/rebuild_fts.py`。
- `SERVER_VERSION = "0.1.0"`（`server.py:22`），库结构已 v6。
- `schema.ensure()` 版本号相同就直接返回，不校验表/列完整性；手工删表后不会自愈。
- `archive._known_projects()` 是永不过期的进程级缓存（`archive.py:142-153`），MCP 长驻期间新建项目不参与 `guess_project`；`projects.scan_dirs()` 有 60s TTL，两处不一致。
- `guess_project` 兜底 `return tail` 会把任意 cwd 尾段当项目名，可能造孤儿项目。
- `delete_project()` 不清理页面层 `pages` / `chunks`，删项目后 `pages_index` 仍能查到。
- `_resume_hint` 只捕 `ValueError`，`started_at` 为 naive 字符串时 `TypeError` 会冒泡。
- `GET /api/memory`、`POST /api/remember` 两个端点前端从未调用（死代码 + 多两个可写入口）。
- `client.js` 拖动监听在「鼠标移出窗口后松开」时不清理；`flash` 的 `setTimeout` 不复位。
- 插件全部 UI 文案硬编码中文，`locale/*.json` 只有 meta，切英文界面仍是中文。
- `cli.py` 有未提交改动 + 未跟踪的 `cli.py.bak-20261105-hook`，建议提交或清掉。
