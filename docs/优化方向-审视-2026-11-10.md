## 0 · 总评

真正的问题不是方向，而是**两个乐观估计**：
- 把「会话源」当成一个文件格式问题，实际是**五个字段级契约**；
- 把「store.py 拆层」当成第一步，实际**内核骨架已经存在**，缺的是接口和依赖方向约束。

## 2 · 会话源的耦合比文档描述的深

`archive.py` 对 DSH 的依赖不是一个文件名，是**五层**：

1. 路径与压缩：`~/.dsh/sessions/*/*/session.v4.jsonl.zstd`，单帧 zstd；
2. 事件类型：`session` / `session/title` / `user/message` / `assistant/message` / `tool/call`；
3. `user/message.source.kind` 白名单：`user` / `compact-checkpoint` / 其余进 `ignored` 计数；
4. 度量字段：`usage.inputTokens`、`usage.cacheReadTokens`（`insight.py` 直接依赖这四个字段算命中率）；
5. 时间：`header.createdAt` 是**整数毫秒**，缺失时退回文件 mtime。

所以 P1 的「录一个样本做 fixture」不够。契约测试至少要覆盖：
- 中文/英文混排与超长会话（zstd 帧边界）；
- `compact-checkpoint` 存在与不存在两种会话；
- `usage` 缺失的旧会话（应判为「无度量」而不是解析失败）；
- 未知事件类型（应忽略且计数，而不是中断）。

**建议**：fixture 用「脱敏后的真实样本 + 一个合成的最小样本」，前者防格式漂移，后者让契约可读。

## 3 · 依赖图的发现（文档没有，但决定拆层顺序）

刚跑的 import 图：

```
card / schema / embed / paths  → 零内部依赖   ← 内核骨架其实已经存在
store   → card, embed, pages, paths, projects, schema
archive → embed, paths, projects
insight → archive, paths                      ← 度量层依赖会话解析器
cleanup → （零 import，直接拿 store._conn）    ← 寄生层
```

四个可直接落地的结论：

1. **`card` + `schema` + `embed` + `paths` 已经是纯净内核候选**，不需要「拆」出来，只需要**定义它们对外的接口**，然后把 `store` 变成「内核 + SQLite 实现」。
2. `store` 依赖 `pages` 仅仅是为了在 `__init__` 里 `ensure_tables`——页面层是独立子系统，应该由调用方装配，而不是 store 兜底。
3. `insight` 依赖 `archive`（会话解析器）。抽 `SessionSource` 后，`insight` 必须改成依赖接口，否则「通用引擎」的度量层还是绑死 DSH。
4. `cleanup` 零 import、直接操作 `store._conn` —— 它是**拆层时最容易漏的一块**（行为在 SQL 里，不在类里）。拆之前先给它一个显式的 Repository 协议，否则 P2 的重放测试覆盖不到它。

## 4 · 优先级建议调整

文档路线：P0 契约设计 → P1 fixture → P2 拆 store → P3 第二实现 → P4 平台 → P5 格式。

我建议**插一个 P0.5，并把 P2 改法**：

### P0.5（新增，<1 天）：边界图 + 依赖方向 CI

把上面这张 import 图变成一条 CI 检查：`core`（card/schema/embed 的抽象部分）不许 import `adapters`（archive/os/dsh）。成本极低，作用是**防止重构期间新代码继续反向依赖**——没有这条约束，拆完一个月又长回去。

### P2（改法）：先协议，后拆文件

不要按文件拆（`store.py` → `store1/store2`），而是：

1. 抽出 `Repository` 协议：`save / get / search / supersede / list_by_namespace`——**只有 6 个方法**；
2. `Store` 内部改成实现这个协议，行为零变化；
3. 把 `cleanup` / `pages` / `insight` 改成依赖协议，而不是 `store._conn`。

文档里的「重放对比」要具体化，否则不可执行：

```
录一份真实库快照（5 MB）+ 30 条调用序列（remember/recall/pack/cleanup/restore 各 6 条）
→ 重构前后各跑一遍 → 断言：返回 JSON 逐字节一致 + 库的 dump（sorted）一致
```

## 5 · 文档漏掉的 5 个耦合/风险

1. **归属键（project）绑定了目录语义**。`projects.normalize` 以 `Projects/<目录名>` 为权威，这是 DSH 的世界观。通用引擎必须把它降级成 `namespace: str`（project 只是其中一种取值），否则 companion-bot 合流时要动 schema（v7 迁移）。
2. **文件系统副作用在核心层**：`store.put_handoff()` 末尾会写 `交接卡.md`。核心层不应该碰文件——通用引擎里这应该由宿主/适配器订阅 `handoff.updated` 事件来做。
3. **`cli.py` 是宿主桥，不是稳定 API**。面板走 `/dsh-rag/api/*` → `cli.py`，而不是 MCP。这意味着每接一个新宿主就要再写一套桥。通用化时应把「面板需要的读模型」收敛成引擎 API（MCP resources 或独立 HTTP），`cli.py` 降级为「运维 CLI」。
4. **没有「同一命名空间的并发写」语义**。现在两个进程同时写同一项目，靠 `content_hash` 唯一约束和 `busy_timeout` 兜底。多宿主是通用引擎的前提，这个问题会立刻暴露——至少在文档里要写成已知边界。
5. **pack 格式文档化时必须写裁剪策略**。`card.build_pack` 的 `next → facts → card` 收缩顺序、facts 从尾部保留、`budget_tokens` 的字符换算（1.6 字符/token）都是隐式行为。不写进规范，消费方无法预期「我拿到的包为什么少了这一段」。

## 6 · 对「通用引擎」的具体形态建议

**最小契约只要 4 个动词 + 2 个概念**：

```
remember(namespace, kind, title, content, meta?) -> id
recall(namespace, query, limit, kinds?) -> Memory[]
pack(namespace, budget_tokens?) -> Pack
checkpoint(namespace, patch) -> Handoff
```

概念：`namespace`（取代 project）、`kind`（decision/pitfall/fact/todo/session/handoff/checkpoint）。

MCP 工具面现在已经是这个形状——说明抽象方向没错，只是**名字绑定了宿主**。

**分层建议**（对应文档的 A/B/C）：

```
engine/core       card / schema / lifecycle / pack    ← 零 IO，纯函数 + 协议
engine/store      SQLite 实现 Repository
engine/search     FTS + vector + RRF（依赖 core，不依赖宿主）
adapters/dsh      SessionSource(DSH) / os 集成
adapters/host     plugin / cli / mcp server
```

## 7 · 同意「不做」，并补三条

文档的「明确不做」四条我都同意。再补三条：

- **不为通用性做多租户/权限**。单机单用户是正确边界；多租户会把 schema、检索、清理全拖进泥潭。
- **不在内核里做「记忆自动合并/自动删」**。矛盾检测可以给接口，但不能自动执行——这是产品信任问题，不是技术问题。
- **不在 P3 之前写第二个 SessionSource 以外的适配器**。Markdown 源够验证接口；其它 harness 等有真实用户。

## 8 · 一句话结论

**按文档做，但把顺序调成：P0 契约 → P0.5 依赖约束 → P1 fixture（五层字段全测）→ P2 协议化（不是拆文件）→ P3 Markdown 源 → P4 平台/HTTP → P5 格式与合流。** P2 之前别碰 cleanup 阈值和 pack 排序；P2 的验收标准是「重放逐字节一致」，不是「测试还是绿的」。

## 9 · 工期口径（2026-11-11 补）

本文与原始《优化方向》里写的「1–2 天」「3–5 天」是**按人类业余时间估的**。
实际执行由 AI 完成，git 时间线约 36 分钟跑完 P0–P5——两者不是矛盾，但引用时请注明口径：

- 引用「工期」时，说「人工等效」；
- 引用「实际耗时」时，用 git 时间线；
- **验收判据与工期无关**：重放逐字节一致、fixtures 全绿、依赖边界干净，这些不因为跑得快就不成立。

同一份文档里既写「P0 需要 1–2 天」又被人拿 git log 对时间线，会被读成虚报；补这一节是为了避免这种误读。
